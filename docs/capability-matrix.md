# Capability and Maturity Matrix

This document is the complete product map for Eqiora. It records both the
bounded capabilities that exist today and the deliberately broader destination:
one coherent platform spanning multiphysics CAE, system simulation and control,
acausal physical modeling, optimization, scalable execution, and an excellent
interactive modeling environment.

It is not a marketing checklist. A feature is only marked as verified when a
reproducible case supports the exact stated scope. The authoritative claims and
non-claims remain the case manifests under [`verify/`](../verify/); this matrix
is their navigable, whole-product index. A manifest's non-claims bound that
case and not the implementation, so the union of the manifests is the lower
bound on what exists rather than any one of them;
[published benchmarks](benchmarks.md) reads them that way. Planned work is described here so that
new implementation fits the final architecture instead of creating parallel
semantics.

The destination has six non-negotiable properties: one canonical meaning
across every authoring surface; implicit and acausal mathematics without
special-case kernels; explicit realization and hardware placement; derivatives
derived from the same lowered operators; immutable evidence for every result;
and an accessible GUI that reveals complexity progressively without hiding it.
Breadth is valuable only when these properties remain intact.

## A first visit

If you are deciding whether Eqiora is relevant to you, read this document in

   row, the final column states the current boundary first and the important

Each heading and status is self-contained; no prior project context is
assumed.

## How to read the matrix

| Mark | Meaning |
|---|---|
| ✅ | Present for the exact scope stated in the row |
| 🟨 | Narrow, provisional, design-only, or incomplete |
| ⬜ | Not implemented |
| — | Not applicable |

Each capability is judged along four independent gates:

| Gate | Question |
|---|---|
| **C — Contract** | Is there a typed, versioned semantic or lowered contract? |
| **X — Execution** | Does at least one real end-to-end path execute? |
| **V — Verification** | Is there reproducible evidence for the stated claim? |
| **M — Maturity** | Is the capability broad, robust, documented, performant, and suitable for general users? |

A ✅ under **X** never silently widens a narrow case into general support. A ✅
under **V** means a bounded claim is verified, not that the product area is
finished. Eqiora is alpha, so no technical product area is currently marked
fully mature.

### Python parity: can the complete model be built in Python?

Not completely. Python can compile Eqiora source and can now natively define a
narrow scalar model from frozen Fields, Parameters, continuous multi-residual
Relations, and nominal scalar physical Domains, conserving Ports, accessors,
and N-ary Connections. It also defines one bounded Cartesian scalar-elliptic
profile from box/boundary Domains, a continuum Representation, supported
Fields/Relations, and `grad` / `div` / `trace`. Both authoring routes cross an
explicitly selected wire, commit, and round-trip the resulting canonical
model. The ordinary scalar path executes the bounded reference interpreter and exposes NumPy
results; the first physical execution proof remains the registered Rust
parallel-DC path rather than a second Python solve surface. The spatial Model
can now enter one bounded Python scalar-elliptic application surface: an
FEM/FVM request is previewed into an opaque exact-model-bound Realization and
executed synchronously on the host-serial reference path. The result contains
complete primary 1D--3D Cartesian Field values, logical shape, summaries, and
exact Run provenance, but not coordinate/mesh arrays, non-Cartesian or
nonuniform layouts, or a general
solver/Realization graph API. Clocks, events, broader spatial/tensor operators,
components, and studies still require source or future typed declarations.
The mature goal is complete authoring and study
orchestration without requiring Eqiora source text, while still crossing the
same versioned transactions as every other client.

## Maintaining this document

- A new ✅ under **V** must link to a reproducible case in [`verify/`](../verify/)
  whose manifest states the same bounded claim and its non-claims.
- A typed name in an RFC may justify 🟨 under **C**, but not ✅ under **X** or
  **V**.
- A backend target, solver name, file format, or GUI control is not support by
  declaration. It graduates only through the same path as every other feature:

  ```text
  meaning → lowered contract → realization → adapter → evidence
  ```

- Mature status requires a public compatibility promise, documentation,
  diagnostics, performance and scale evidence, supported-platform coverage,
  and real-user operation—not merely more code.
- Update this matrix in the same change that adds or removes a capability
  claim. Keep detailed sequencing in the [`roadmap`](roadmap.md), architectural
  invariants in [`architecture.md`](architecture.md), and executable truth in
  [`verify/`](../verify/).
- The root [`AGENTS.md`](../AGENTS.md) and
  [`CONTRIBUTING.md`](../CONTRIBUTING.md) make that update part of the
  repository-wide definition of done for agents and human contributors.
